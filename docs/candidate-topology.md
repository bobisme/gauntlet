# Candidate worker and verifier topology

This is a local experiment, not isolated-custody or enforcement qualification. It runs a packaged fixture and two pinned Teapot engines using the same physical Hallpass pass. The rootless worker has a read-only mount containing one Unix socket. A referee-owned relay forwards that socket to the exploration engine's proxy listener. The worker has `--network=none`, a read-only root filesystem, no capabilities and no-new-privileges. It logs in as alice and bob with the development credentials and probes `/app/api/me` through that proxy. No instrument control socket, project directory, pass, verifier session, or verifier flow query is mounted. There is no flow-query broker in this experiment.

The referee creates both verifier sessions in a second Teapot project and sends and reads back an alice-verify identity flow. The packaged fixture's opt-in `--private-verifiers` generates independent 256-bit random passwords in `verifier-passwords.json` (mode 0600 in the 0700 package). Only the referee and fixture read this file. Reset preserves those credentials while clearing state and sessions. The ordinary fixture package still uses documented development passwords; it is unsuitable for a separate-principal experiment. Passwords are sent in the referee's local Teapot command arguments and stored in its flow database: protect the operator account, process inspection, and all referee files. This experiment does not isolate against the host operator or other same-UID host processes.

The worker probes the exact host paths of both project stores, pass, source, ground truth, administration secret, and verifier-password file, and tries direct connections to the target and verifier listener. It also attempts both publicly documented default verifier passwords via the exploration proxy. These are narrow probes, not proof that all routes or credential guesses are impossible. The exploration proxy can send arbitrary requests within the instrument's allowed scope, including to the fixture's login and administrative endpoints. The fixture's state can still be changed using exploration principals; no flow isolation against target-side state contamination is established. The worker image, kernel, Podman, relay and host remain trusted. The eight M0.5 tamper attempts, concurrent activity, and a model agent are not qualified here.

Both engines use `--no-enforce`: loopback is not enforced by Playpen. The observed allocator counters are especially important: exploration proxy traffic was served despite its project reporting zero requests handed and zero drawn. The verifier's three explicit sends drew a block of 10 and handed 3; the Hallpass ledger reported 10 spent. Do not infer a request ceiling, a pass-wide request count, or enforcement from those values. The earlier [two-project experiment](two-projects-pass.md) showed that two direct-send projects each drew a 10-unit block; unused allocation and displayed counters are project/lifecycle-specific and can diverge. Concurrent draws, crashes, restart and exhaustion remain untested.

## Run

Use Linux with rootless Podman, a working user namespace, cached `docker.io/library/python:3.12-alpine`, Cargo dependencies, and the pinned offline-built Teapot and Hallpass binaries. The trial does not install software or run privileged setup. See [rootless prerequisites](../evals/README.md#rootless-worker-read-qualification). The pinned binary hashes are checked by the harness. From this workspace:

```sh
python3 scripts/candidate-topology.py \
  --teapot /absolute/path/to/pinned/teapot \
  --hallpass /absolute/path/to/pinned/hallpass > result.json
```

The script builds and runs the real fixture package with an ephemeral loopback port, creates a short-lived locally approved pass, runs both engines and the worker, reads the ledger and project counters, then stops the engines and fixture and verifies container removal. Cleanup uses only the validated container ID from its private `--cidfile`, never the name. If the ID is missing or malformed, cleanup reports the generated name for manual inspection and does not remove a container. It removes its private temporary files on successful teardown; on a detected cleanup failure it retains the referee directory and reports its location. Abrupt SIGKILL, host failure and process-ID reuse are not qualified cleanup cases; inspect and recover any named `scourge-topology-*` container and retained referee directory after an interrupted run. Standard output is the redacted observation JSON, emitted only after successful teardown, and includes the script hash. `python3 -B scripts/test-candidate-topology.py` validates the committed observation and exercises cleanup with a fake Podman, including the missing-ID case.

The recorded local run is [candidate-topology-observed.json](../fixtures/contracts/candidate-topology-observed.json). It exited 0 on Podman 6.1.3 with the recorded image and binary hashes. Both public verifier passwords returned 401, both worker identity probes returned 200, the verifier's stored identity flow returned 200, the seven path probes failed ENOENT, and direct TCP probes failed. The run's fixture reset preceded verifier login. A separate regression test exercises password rejection and acceptance both before and after reset. Container removal and both engine stopped states were checked in teardown. This is one local observation; parent-death and interruption cleanup have not been independently fault-injected for this harness.
