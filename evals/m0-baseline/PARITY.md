# M0 A/B visible-input contract

**Frozen:** 2026-11-22, before the first scored M0.4 baseline run. The hashes in `materials.lock.json` identify the static bytes. A changed byte requires a new lock and invalidates comparison with runs under the prior lock.

Both arms receive the same base agent and model settings, target instance from the same reset state, host and target permissions, system and wrapper messages, environment variables, process limits, time and request budgets, retry policy, network routes, executable search path, native instrument, task, engagement facts, report expectations, workspace layout, and initial screen. The only assigned difference is that condition B can read `condition-b/methodology.md`; condition A cannot. The condition-B file is prose guidance: it supplies no executable, structured run state, verifier, fixture answer, expected finding count, case label, object identifier, marker, or named principal pair.

The static common files are `common/task.txt`, `common/engagement.json`, and `common/report-template.md`. They are copied byte-for-byte to each arm. The worker tree contains no source checkout, ground truth, administration or verifier credentials, previous transcript, expected-positive or expected-negative label, managed `AGENTS.md` block, extra example, or arm-specific report template. Only the native Teapot CLI's built-in help, guide, and schema are instrument documentation; neither arm receives Teapot source or repository prose.

The engagement lists every fixture resource class and its policy in the same form. No resource is described as flawed, suspicious, a control, a decoy, or a lead. The account list supplies an unpaired pool of exploration accounts; verifier accounts are withheld. If a runner adds a resource-specific property, named pair, candidate route, example finding, or other input that points at a case, every affected session is reclassified as supplied-lead and is not part of this discovery comparison.

At run start the referee must record and compare both arms' actually visible file names and SHA-256 hashes, task bytes, effective prompts and loaded instructions, first screen, tool inventory and versions, model configuration, target/reset identifier, permissions, budgets, retries, and environment allowlist. The Teapot executable must report `teapot 0.1.0`, hash to the pinned digest, and be the executable reached from `PATH`. A mismatch stops the matched group; it is not repaired after seeing an outcome. The run record identifies this materials lock and hashes the additional condition-B file separately.

Each individual session receives a newly created Teapot project and store under a newly created run-private directory. The runner also supplies fresh, empty `HOME`, `XDG_CONFIG_HOME`, `XDG_STATE_HOME`, and `XDG_DATA_HOME` directories. The project path must not exist before `projects init`; a project, store, home, XDG directory, pass ledger, engine, or agent workspace is never copied or reused across sessions or arms. The runner records their creation and unique run identity, refuses a pre-existing path or ledger, and removes them from the eligible pool after one launch even when that launch fails. This makes cross-arm reuse a setup failure rather than a source of hidden history.

Before the agent launches, the runner configures only the matched baseline state: one initialized project, the run's approval attached, scope containing only the fixture destination, no host pins, and one running exploration proxy. There are no captured flows, findings, leads, sessions, user rules, intercept rules or queued intercepts, macros, jobs, sitemap entries, authorization-matrix rows, user or project scripts, or trusted script approvals. The pinned default intercept status is retained and compared; it reports enabled with zero rules, zero active rules and zero paused requests. Configuration is the pinned defaults plus the recorded pass, scope, listener, and no-enforcement settings required by the qualified loopback topology. The pinned native checks, lead rules, and built-in scripts remain present and must be identical; they are not treated as empty state.

Eligibility is executable, not an operator interpretation. The projector requires the pinned engine to answer in regular mode, running with a pass and a lifetime policy lock, with Playpen enforcement off for loopback. It requires exactly the `127.0.0.1/*` scope, the run-private `pass.path`, the matching serialized scope setting, the fixture approval's sole `127.0.0.1:3000` destination and unspent 1,000-request ceiling, a bound and valid gate, no upstream proxy, no newer or stopped approval, enabled interception, zero meaningful error/refusal/drop/queue/traffic counters, and the locked native script, lead-rule, check and authorization-matrix-legend identities. The approval source is the explicit `--pass` used for the locked proxy lifetime. A missing pass object, altered scope, extra setting, unlocked policy, enforced or non-regular proxy, disabled interception, upstream proxy, non-native script/check, or any other configured-state mutation makes `prelaunch.eligible` false even when both arms were mutated alike.

The referee captures raw JSON immediately before launch for `version`, `projects list`, `projects show`, `proxy status`, `pass show`, `scope list`, `hosts list`, `flows list`, `findings list`, `leads list`, `sessions list`, `rules list`, `intercept status`, `intercept rules list`, `intercept queue list`, `scripts list`, `scripts approvals`, `config list`, `macros list`, `jobs list`, `sitemap show`, `authz matrix`, `checks list`, and `commands list`. Unsupported inventory commands fail setup; they are not silently omitted. It verifies the empty and configured conditions above and retains every raw response and its hash. Host pins must be empty in every run; a nonempty or unequal `hosts list` invalidates the group.

Cross-arm equality uses the checked-in v1 projector, `project_inventory.py`, not the full raw `proxy status`. The projector selects configured inputs; logical empty-state verdicts; the complete rule contents; script, hook, check, lead-rule and command identities and enabled/replacement states; exact scope and host pins; pass destinations, ceilings and meaningful counters; configuration key/value/source state; and meaningful zero/error/refusal/drop/queue/connection/job/request counters. It sorts object keys, sorts set-like arrays by their real schema-backed identity, preserves order where the command contract makes order meaningful, serializes compact UTF-8 JSON, and hashes those bytes with SHA-256. Unknown envelope, object or row fields fail projection. A wildcard in an exclusion pointer matches exactly one numeric array index and is never recursive. The run record contains the locked projector hash, projected JSON and digest; use `python3 -B evals/m0-baseline/project_inventory.py RAW_INVENTORY.json` to reproduce it.

The raw telemetry remains evidence but does not decide parity. The locked exclusion list names the volatile proxy engine paths and health timestamps, disk-capacity and store-size samples, WAL byte and latency samples, log path and byte counts, file-descriptor/runtime/task samples, uptime, and per-check or per-script performance counters. The code and lock also enumerate `/proxy/project` and every independently generated approval path, digest, ID and validity field that is excluded or normalized. No unlisted path is silently dropped: an unknown field makes projection fail until the code and lock explicitly select, normalize or exclude it. In particular, rules, scripts, checks, scope, host pins, pass ceilings and meaningful safety counters may not be removed as telemetry. Approval variants are normalized only after their destination, ceiling, enforcement and lock semantics are selected elsewhere in the projection.

Both arms' run records contain the raw-inventory artifact hashes, semantic projection, projection digest, empty-state verdict, project/store creation evidence, and exact projection rules. A matched A/B group is valid only when the semantic digests are equal and all empty-state assertions pass before either agent launches. The condition-B prose file is added after this comparison without changing instrument state. Any initial semantic mismatch, unknown field, pre-existing state, reuse, or inventory read failure invalidates the matched group before outcomes are inspected.

This contract freezes inputs, not results. It does not establish that a run was hermetic, that the target reset succeeded, or that an agent used the supplied facts. Those are runtime observations recorded by the harness.

The checked-in `qualification/evidence/` is the pre-registration witness for this projector, not a baseline result. `qualification/capture_fresh_pair.py` creates two distinct run-private roots, empty HOME/XDG trees, project stores and approval copies; records every setup and inventory command; captures schemas for all 24 projected commands and the raw inventories; projects both; stops both proxies; verifies `proxy status` reports `running: false`; and only then removes the run roots. The start-attempt flag is set before dispatch, so cleanup still stops and probes a detached proxy when response handling fails after launch. Proxy-stop, termination-verification, or root-removal failure makes capture fail. Its manifest hashes the raw, projected, schema, creation and command artifacts, attests distinct project IDs and raw hashes, and records an equal eligible semantic digest. The validator recomputes those attestations and cross-checks declared project identities, paths, digests, and successful cleanup against raw evidence. Reproduce it into a new, nonexistent output directory with `python3 -B evals/m0-baseline/qualification/capture_fresh_pair.py --teapot PATH_TO_PINNED_TEAPOT --output-dir NEW_DIRECTORY`. The script verifies the pinned binary hash before use, starts no assessment agent and sends no target request.
